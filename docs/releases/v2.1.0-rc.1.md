# modelpull v2.1.0-rc.1 — Release Notes

> **Release date (RC)**: 2026-05-27
> **GA gate**: pending the 7-day staging baseline + 4 chaos drills (see
> `docs/operator/v21-production-deployment.md`)

## What's new

v2.1 adds five major capabilities, all gated by feature flags so the
upgrade itself is non-disruptive:

### 1. SLA tier scheduling (Sprint 1)

Every tenant now carries an `sla_tier` (one of `critical` / `standard` /
`bulk`, default `standard`). The scheduler weights queue order by
`tier_weight × (priority + 1)`, with a 30-minute starvation bump that
upgrades any bulk task's weight ×2 if it's been waiting too long.

Quota admission control rejects new bulk tasks when the system is > 90%
busy and standard tasks when > 99% busy; critical never rejects.

- REST: `PUT /api/v1/tenants/{id}/sla` (`system_admin` only)
- UI: settings page lets admins flip the tier; readonly tag otherwise
- Feature flag: `DLW_SLA_TIER_ENABLED` (default false in clean
  installs; new tenants default to `standard`)

### 2. Physical garbage collection (Sprint 3)

Replaces the v2.0 logical-only GC with a real two-phase pass:
  - Phase 1: deletes tombstone (refcount=0) physical objects from S3 /
    local FS via the storage driver
  - Phase 2: LRU eviction down to 90% of `quota_storage_gb` per tenant
    under pressure

Admin REST:
  - `POST /api/v1/admin/gc/run` (system_admin only, audited)
  - `GET /api/v1/admin/gc/status` (last-run summary)

Feature flag: `DLW_PHYSICAL_GC_ENABLED` (default false; flip on after
verifying tombstone counts on staging).

### 3. Cross-region replication (Sprints 4-5-6)

Cross-region copy of a storage_object to another storage_backend:

- Data model + REST: `POST /api/v1/replication` to queue,
  `GET /api/v1/replication?status=...` to list,
  `POST /api/v1/replication/{id}/cancel`
- Background worker (Sprint 5): streams source → target via boto3
  GetObject + PutObject, verifies sha256, retries 3× with exponential
  backoff, respects per-tenant bandwidth (`DLW_REPLICATION_BANDWIDTH_MBPS`
  default 100 MB/s)
- Worker uses FOR UPDATE SKIP LOCKED so multiple controllers can run
  side by side without claiming the same job
- Skip-existing dedup: target's `(tenant_id, storage_id, sha256)`
  UniqueConstraint catches "already there" both proactively (phase 1
  check) and reactively (IntegrityError on phase 3 race)
- Frontend (Sprint 6): `/replication` page (admin-only nav) with list,
  status filter, create dialog, cancel
- AI tool: `dlw_create_replication` (system_admin only, requires
  confirmation) — wires the assistant into the same workflow
- Observability: 3 new Prometheus metrics + Grafana dashboard
  (`deploy/grafana/replication-throughput.json`)

Feature flag: `DLW_REPLICATION_WORKER_ENABLED` (default false; loop is
inert until enabled).

### 4. Adaptive optimizer (Sprints 7-8-9)

Three-stage rollout:
  - **Sprint 7**: per-chunk throughput sampling. New table
    `chunk_throughput_sample` populated on every subtask completion via
    an async-batched in-memory deque (FLUSH_INTERVAL=5s,
    MAX_BUFFER_SIZE=10000). Daily retention deletes rows older than
    `DLW_THROUGHPUT_SAMPLE_RETENTION_DAYS` (default 7).
  - **Sprint 8**: `services/optimizer.py` LPT (Longest Processing Time)
    heuristic + local-swap polish. Solves the assignment problem
    (N chunks × M executors × S sources) with provable 4/3 makespan
    guarantee. Pure Python, zero new dependency — measured ~10ms for
    100×10×5 (budget 1s).
  - **Sprint 9**: `services/replan_loop.py` 30s tick that diffs the
    optimal plan against current `subtask_chunks.source_id` and either
    SHADOW-logs the would-moves or APPLY-writes them. **Two layers of
    safety**: `DLW_ADAPTIVE_OPTIMIZER_ENABLED` (master) +
    `DLW_ADAPTIVE_OPTIMIZER_APPLY` (write gate). Both default false.

### 5. Enterprise-network deploy mode (Sprints 10-11-12-13)

Inbound-restricted executors now dial out over WSS instead of being
polled inbound. Four sub-sprints:
  - **Sprint 10**: protocol + handshake. `/api/v1/exec/reverse-ws`
    WebSocket endpoint with JWT auth, frame schema (`HelloFrame`,
    `HelloAckFrame`, `HeartbeatFrame`, `HeartbeatAckFrame`,
    `ErrorFrame`), in-memory session registry with reconnect-wins
    semantics.
  - **Sprint 11**: task dispatch + reconnect resends. `TaskAssignFrame`
    + `TaskAssignAckFrame` ride the same socket; `ReverseDispatcher`
    keeps a per-executor pending map and resends on
    `on_session_established`. At-least-once delivery — a failed send
    keeps the assignment in pending for next handshake.
  - **Sprint 12**: credential pool + envelope encryption.
    `services/credential_pool.py` central chokepoint for credential
    lookups; Fernet envelope encryption with 4-byte magic prefix
    (`\x1bDLW`) auto-detected. v2.0 plaintext rows pass through
    unchanged — non-breaking migration.
  - **Sprint 13**: Live Console. `CommandFrame` / `CommandResultFrame`
    / `ConsoleOutputFrame` for whitelisted command channel.
    `WHITELIST_COMMANDS = ("status", "drain", "restart")` enforced at
    BOTH the dispatcher and frame layers. Admin REST:
    `POST /api/v1/admin/executors/{id}/command` (system_admin),
    `GET /api/v1/admin/reverse-ws/sessions` (live-connection inventory
    for the xterm.js front-end follow-on).

## Cross-feature integration (Sprint 14)

Twelve integration scenarios in `tests/integration/test_v21_cross_feature.py`
verify the features above interoperate:
  - SLA × admission gate behavior at each threshold
  - Replication × GC reference-count protection
  - Sampler → optimizer end-to-end with real DB samples
  - Reverse-WSS + dispatcher + console full chain (register → dispatch →
    command → reconnect → command continues)
  - Credential pool envelope + legacy plaintext side-by-side

## Upgrade notes

1. Run `alembic upgrade head` — adds three tables:
   `replication_jobs` (S4), `chunk_throughput_sample` (S7), and the
   `tenants.sla_tier` column (S1).
2. Default ALL feature flags OFF — staging-verify each before flipping
   on production.
3. `DLW_CONFIG_KEY` is optional but recommended; without it new
   storage_backends rows stay plaintext (matches v2.0 behavior).
4. Reverse-WSS endpoint requires executors to upgrade to the v2.1
   client; legacy POST /poll path still works for executors that
   haven't.

## Breaking changes

None at the REST API level. Internal `services/replication.py` raises
new exceptions (`ObjectNotFound`, `TargetNotFound`, `InvalidTarget`,
`DuplicateJob`, `JobNotFound`, `NotCancellable`); if you have
out-of-tree code calling these services, update its except clauses.

## Known limitations

- AI assistant's `dlw_create_replication` tool ships in Sprint 6 but the
  result-correlation roundtrip (waiting for `CommandResultFrame` /
  replication-completion broadcast) is a Sprint 14+ follow-on — for now
  it's fire-and-forget on the assistant side; users poll job status.
- xterm.js front-end Live Console is **not** in this release —
  Sprint 13 ships the backend wire + REST surface; the UI follow-on
  reuses the existing Vue + Element Plus pattern from `Replication.vue`.
- Sprint 12 envelope encryption is opt-in per-row; an automatic
  re-encrypt batch job for v2.0 legacy rows is a follow-on (no data
  is at risk — rows just stay plaintext).
