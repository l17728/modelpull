## §1 — Physical GC + LRU 驱逐（v2.1 起步特性）

### 1.1 现状

**v2.0 Phase 4 已实现**：逻辑 GC — 通过引用计数（`subtask_object_refs`）追踪
storage_object 是否还被引用；引用为 0 标 `tombstone`。

**v2.1 待补**：把 `tombstone` 的 object **真正从 object store 物理删除**，且
按 LRU + 配额做主动驱逐（即使引用 > 0，也按 quota_storage_gb 驱逐最久不用的）。

### 1.2 设计

新表 `storage_object_lru`（或在 `storage_objects` 加 `last_accessed_at` 列）：

```sql
ALTER TABLE storage_objects
ADD COLUMN last_accessed_at TIMESTAMPTZ NOT NULL DEFAULT NOW();
CREATE INDEX ix_storage_objects_last_access ON storage_objects(last_accessed_at);
```

每次 `complete_subtask` / `record_object` 调用更新 `last_accessed_at`。

新服务 `services/physical_gc.py`（**本次仅骨架** — 完整实现需上面表迁移 +
真接 S3 API + chaos test）：

- `find_eviction_candidates(tenant_id, target_free_bytes)` — 按 LRU 选要驱逐的
  objects 直到腾出目标空间
- `evict_object(object)` — 调 S3 DeleteObject + 删 storage_object 行
- `gc_run_once(tenant_id)` — 1 轮 GC：先清 tombstone，再按配额 LRU 驱逐
- `gc_loop()` — 后台周期任务（每 `DLW_GC_INTERVAL_SECONDS` 跑一次）

### 1.3 验收标准

- [ ] 当 `tombstone=true` 的 object 跑过 GC 后，S3 上对应 key 真消失（不只是 DB 行删了）
- [ ] 当 tenant 用量超 `quota_storage_gb` 时，自动驱逐 LRU 直到回到 90%
- [ ] 驱逐时不能影响正在引用该 object 的活跃 task（active 引用置位锁住）
- [ ] GC 全过程审计：`physical_gc.evict` / `physical_gc.run` action 进 audit_log
- [ ] 单测覆盖：候选选择算法、驱逐成功、活跃保护、并发安全

### 1.4 本次提交起步范围

仅 **接口骨架 + 配置开关 + TODO**，不动 schema、不接真 S3。完整实现按 1.3 验收
逐项做。

## §2 — 自适应在线运筹优化（v2.1）

### 2.1 设计概要

把 chunk-level 调度从"被动"改为"主动" — 实时收集 (executor, source, file)
三元组的吞吐样本，每 30s 解一个最优化问题：

```
minimize  makespan(plan) + α × switch_cost(plan, current_plan)
s.t.      sum(plan[c].size for c in active_chunks_on_exec_src) <= bandwidth_cap
          plan covers all unfinished chunks
```

参考设计：`docs/v2.0/09-or-optimization.md`。

### 2.2 关键缺口

- **LP solver 选型未定**：CBC / GLPK / Highs。CBC 是默认建议，但 Windows
  pip install 卡（COIN-OR 二进制）。生产用 Highs（纯 C，pip wheel 全平台）。
- **历史样本采集表未建**：要先加 `source_speed_sample` 的更细粒度版本
- **决策频率与 chunk_min_size 的耦合需调整**

### 2.3 实施估时拆分

| 子任务 | 估时 |
|--------|------|
| 历史样本表 + 采样器 | 1 周 |
| LP solver 集成（Highs） | 1 周 |
| 决策循环 + replan 触发 | 1 周 |
| switch_cost 模型 + α 调优 | 1 周 |
| 集成测试（多源失速 / 切换） | 1 周 |
| 性能基线 + 上线 gating | 1 周 |
| **合计** | **6 周** |

### 2.4 阻塞

需要先收集 ≥ 1 周的真实下载吞吐数据来训练 / 校准 switch_cost 模型。**所以
要做这个特性，得先在 staging 跑一段时间 v2.0 收集样本。**

## §3 — 企业内网部署（反向 WSS / 凭证池 / Live Console）

### 3.1 问题域

很多企业的下载执行器在内网防火墙后面，无法从公网 controller 主动连。需要：

- **反向 WSS**：executor 主动连到 controller 的 WSS 端口，controller 通过这个
  长连通道下发任务（反向 RPC）
- **凭证池**：HF token / S3 key 不下发到 executor，而是 controller 代理
  请求（v2.0 W3b 的 hf_proxy 是这个的一部分）
- **Live Console**：管理员在 UI 上看 executor 的实时日志 / 给它发命令（不是 SSH）

### 3.2 现状

- v2.0 W3b 已有 HF 反向代理 — 但不是 WSS 长连，是每次 HTTPS 请求
- mTLS + JWT 已经有了，可以复用作为 WSS 握手鉴权
- Live Console 完全没有

### 3.3 估时

6-8 周，因为涉及新的双向流协议（WSS frame layer）+ controller 端长连状态机
+ executor 端事件循环。**绝对不是一个 session 能搞定的事**。

## §4 — 跨地域复制

### 4.1 问题域

任务在 region A 完成，希望自动同步到 region B 的 object store（同 tenant 不同
storage_id），用户在 B 区可以零延迟拉。

### 4.2 现状

- storage_backends 表已经有 `region` 列
- 但没有 region-aware 调度，没有 cross-region replication job

### 4.3 估时

4-5 周。

---

## §5 — SLA 分级

### 5.1 问题域

Critical 任务优先调度 / 抢占非 critical。priority 字段已有（0-10），但
scheduler **没真用它做优先级**（只是显示）。

### 5.2 改造

- scheduler 在挑下一个 chunk 时按 priority 加权
- quota 加上 "保留 N% 容量给 critical" 的 admission control
- 配套监控指标：每个优先级层的等待时间 / SLO 命中率

### 5.3 估时

2-3 周（最小可行版本）。

## 优先级建议

按"价值 / 风险 / 工程量"排，推荐顺序：

1. **Physical GC**（2-3 周）— 风险低、价值高（避免存储爆掉）、不破坏现有功能
2. **SLA 分级**（2-3 周）— 中价值、低风险、scheduler 是稳定模块
3. **跨地域复制**（4-5 周）— 高价值、中风险
4. **自适应运筹**（4-6 周）— 高价值、高复杂度，需要先有 staging 数据
5. **企业内网**（6-8 周）— 高价值但范围最大，建议独立 sprint

合理 release 节奏：每 1-2 个特性 cut 一个 v2.1.x，不要等到全部完成再 ship。
