完成 [v2.1 路线图](./v2.1-roadmap.md) 列出的 5 大特性：

1. SLA 分级（最小，先做）

3. 跨地域复制
4. 自适应在线运筹优化
5. 企业内网部署（反向 WSS + 凭证池 + Live Console）

最后一个 sprint 是 **跨特性集成 + 生产部署烟测**。

## Sprint 计划详细

### Sprint 1 — SLA 分级（2 周）

**目标**：按租户 SLA tier 优先调度任务，critical 抢占非 critical。

**范围（代码）**：
- 新列 `tenants.sla_tier` enum: `critical` / `standard` / `bulk`（默认 standard）
  - Migration: `xxxx_add_sla_tier.py`
- `services/scheduler.py` 改造：挑下一个 chunk 时按 (priority × tier_weight) 加权
  - tier 权重：critical=4, standard=2, bulk=1
- `services/quota.py` 新增 `admission_control`：当系统并发占用 > 90% 时，
  只接 critical/standard，拒 bulk（429 + 重试时间提示）
- REST `PUT /api/v1/tenants/{id}/sla` (system_admin only, audit-logged)
- Prometheus metrics：`scheduler_queue_wait_seconds` 按 sla_tier 分桶
- 前端 Settings → 显示当前 sla_tier（admin 可改）

**验收标准**：
- [ ] migration 双向（upgrade/downgrade）通过
- [ ] critical tenant 的任务永远先于 bulk 进 active 队列（单测验证）
- [ ] admission control 在 quota 紧张时按 tier 拒绝（集成测试 + Grafana 看 metric）
- [ ] 所有 sla_tier 变更进 audit log
- [ ] 端到端：建 3 tenant（每 tier 一个），并发提交，看完成顺序
- [ ] 文档：`docs/operator/sla-tier-setup.md` + MANUAL 加章节

**代码量**：~600 行 + ~250 行测试

**依赖**：无

**风险 / 回滚**：
- 风险：scheduler 权重改错可能让 bulk 永远饿死。
- 缓解：bulk 加 starvation timeout（30 分钟未调度强制晋升）
- 回滚：feature flag `DLW_SLA_TIER_ENABLED`（默认 false），关掉退回原行为

**Sprint 末交付**：v2.1.0-alpha.1 tag

### Sprint 2 — Physical GC Part 1：存储抽象 + LRU 元数据（2 周）

**目标**：为 Physical GC 铺路 —— 加 LRU 列、补全存储 driver 接口。

**范围**：
- Migration：`storage_objects` 加 `last_accessed_at TIMESTAMPTZ NOT NULL DEFAULT NOW()` + index
- `services/storage_drivers/base.py` Protocol 加 `delete(key) -> bool`
- `services/storage_drivers/s3.py` 实现 `delete()` (调 S3 DeleteObject)
- `services/storage_drivers/fs.py` 实现 `delete()` (os.unlink)
- 改造 `complete_subtask` / `record_object` 路径更新 `last_accessed_at`
- 单测：driver delete / last_accessed 更新

**验收标准**：
- [ ] Migration 双向通过
- [ ] S3 delete + fs delete 单测通过（fs 用临时目录；S3 用 moto mock）
- [ ] 既有功能不受影响（v2.0 全量回归绿）

**代码量**：~400 行 + ~200 行测试

**依赖**：Sprint 1（不强依赖，但建议串行避免合并冲突）

**风险**：last_accessed_at 更新可能成为热点（高 QPS 写）—— 用 PG 的
`UPDATE ... WHERE last_accessed_at < NOW() - INTERVAL '1 minute'` 限频。

### Sprint 3 — Physical GC Part 2：执行引擎 + REST 端点（2 周）

**目标**：真把 tombstone object 物理删除 + LRU 主动驱逐。

**范围**：
- `services/physical_gc.py` 替换骨架为真实现：
  - `find_tombstone_candidates()` 真查询
  - `find_lru_eviction_candidates()` 按 tenant quota 找候选
  - `evict_one()` 调 driver.delete + 删 DB 行（FOR UPDATE 锁）
  - `gc_run_once()` 编排：先 tombstone，再 LRU
- 后台 cron loop（lifespan 任务，每 1 小时跑一次；可配）
- REST：
  - `POST /api/v1/admin/gc/run` (system_admin only) — 手动触发
  - `GET /api/v1/admin/gc/status` — 上次跑的结果摘要
- 审计每次 evict（action="physical_gc.evict"，payload 含 object_id/size/reason）
- 配置：`DLW_PHYSICAL_GC_ENABLED` (default false 上线先观察), `DLW_GC_INTERVAL_SECONDS`,
  `DLW_GC_LRU_TARGET_FRACTION` (默认 0.90)

**验收标准**：
- [ ] tombstone object 跑过 GC 后 S3 真消失（minio 实测）
- [ ] tenant 用量超 quota_storage_gb 时自动驱逐到 90%
- [ ] 活跃引用保护：正在被运行任务引用的 object 永不被选中（race 测试）
- [ ] 部分失败不破坏一致性：S3 删了 DB 删失败时能下次重试
- [ ] 审计完整
- [ ] 端到端：上传 100 个 task 然后删除，跑 GC，S3 桶变空

**代码量**：~600 行 + ~400 行测试（含 minio 集成测试）

**依赖**：Sprint 2 必须完成

**风险**：
- 误删活跃 object 损失数据 —— 多重保护：FOR UPDATE + 双重检查 + dry-run flag
- S3 API 限流 —— 批量删用 `DeleteObjects` (一次最多 1000)，加 backoff

**Sprint 末交付**：v2.1.0-alpha.2

### Sprint 4 — 跨地域复制 Part 1：数据模型（2 周）

**目标**：让系统能描述 "region A 的对象 → 复制到 region B"，但不真复制。

**范围**：
- 新表 `replication_jobs`:
  ```sql
  CREATE TABLE replication_jobs (
    id BIGSERIAL PRIMARY KEY,
    tenant_id BIGINT NOT NULL REFERENCES tenants(id),
    source_object_id BIGINT NOT NULL REFERENCES storage_objects(id),
    target_storage_id BIGINT NOT NULL REFERENCES storage_backends(id),
    status VARCHAR(32) NOT NULL DEFAULT 'pending',
    created_at TIMESTAMPTZ DEFAULT NOW(),
    completed_at TIMESTAMPTZ,
    bytes_transferred BIGINT DEFAULT 0,
    error_message TEXT
  );
  ```
- `services/replication.py` 接口骨架（参考 physical_gc 模式）
- REST `POST /api/v1/replication/jobs` (admin only) — 手动创建
- REST `GET /api/v1/replication/jobs` — 列表 / 状态查询
- 不真跑 transfer（Sprint 5 做）

**验收标准**：
- [ ] Migration 通过
- [ ] 能 create + list job，状态停在 `pending`
- [ ] 跨租户隔离（A 看不到 B 的 replication job）

**代码量**：~400 行 + ~200 行测试

**依赖**：Sprint 2（复用 storage driver 抽象）

### Sprint 5 — 跨地域复制 Part 2：实际传输（2 周）

**目标**：真把 object 从 region A 复制到 region B。

**范围**：
- `services/replication.py` 真实现：
  - `execute_job(job)` 流式 read from source driver → write to target driver
  - 进度报告（每 10 MB 更新 `bytes_transferred`）
  - 失败重试（最多 3 次，指数退避）
  - 完整性校验（target 写完后比对 sha256）
- 后台 worker loop 拉 pending job 跑
- 限速：每 tenant `replication_bandwidth_mbps` 配置（默认 100MB/s）
- 冲突解决：target 已有同 sha 的 object → 跳过（标 `skipped_existing`）

**验收标准**：
- [ ] 单 job 完成后 target 存在 + sha 匹配
- [ ] 部分失败可重试，sum(bytes_transferred) 不重复计算
- [ ] 限速生效（带宽探针验证）
- [ ] 多 job 并发不互相干扰

**代码量**：~600 行 + ~300 行测试

**依赖**：Sprint 4

### Sprint 8 — 自适应优化 Part 2：LP solver 集成（2 周）

**目标**：把 chunk 分配建模为 LP 问题，能解出最优方案。

**范围**：
- 新 pip dep：`highspy>=1.6`（纯 Python wheel，全平台 OK）
- `services/optimizer.py`：
  - 构建 LP：决策变量是 (chunk, executor, source) 三元组的 0/1 分配
  - 约束：每 chunk 必须被分配；每 (executor, source) 带宽不超过实测均值
  - 目标：minimize makespan + α × switch_cost
- 不接到调度器（Sprint 9 做）—— 这一个 sprint 只验证求解正确性

**验收标准**：
- [ ] 给定合成输入，求解结果手算可验证
- [ ] 性能：100 chunk × 10 executor × 5 source 在 1s 内求解
- [ ] 退化情况：单 executor / 单 source 时退化为顺序分配

**代码量**：~500 行 + ~250 行测试

**依赖**：Sprint 7（用真实样本数据做 benchmark）

### Sprint 9 — 自适应优化 Part 3：在线 replan（2 周）

**目标**：把 optimizer 接到运行中的调度，每 30s 重规划。

**范围**：
- `services/replan_loop.py`：30s tick + 事件触发（executor 加入 / 退出）
- 把求解结果差异化应用：只搬变化的 chunk，不动正在跑的
- switch_cost 模型 + α 调优（多次小流量灰度）
- Feature flag `DLW_ADAPTIVE_OPTIMIZER_ENABLED`（默认 false）
- 监控指标：`optimizer_solve_duration_ms`、`replan_chunk_moves_total`

**验收标准**：
- [ ] 多源失速场景：优化器在 1 个周期内 reroute 到健康源
- [ ] 不破坏运行中 chunk
- [ ] 与 v2.0 默认调度 A/B：makespan 平均改善 ≥ 20%（小流量灰度数据）

**代码量**：~600 行 + ~300 行测试

**依赖**：Sprint 8

**Sprint 末交付**：v2.1.0-alpha.4

### Sprint 10-13 — 企业内网部署（8 周，最大块）

- 验收：执行器进程内存 dump 不含任何 production token

**Sprint 13**：Live Console + 前端
- 通过 WSS 双向流：UI ←→ controller ←→ executor stdout
- 前端 xterm.js 渲染
- 命令下发（仅白名单：restart / drain / status）
- 验收：在 UI 能实时看到 executor 日志，能远程 drain

## 每个 sprint 末必做的事

1. 在 staging 部署，跑 24h
2. 跑完整 QA test plan（[`qa-test-plan.md`](./operator/qa-test-plan.md)）
3. 更新 CHANGELOG.md
4. cut 一个 git tag（v2.1.0-alpha.N）
5. 30 min retro：哪些 sprint 估时偏离？为什么？

## 失败 / 滑期处理

任何 sprint 滑超过 1 周，**不要试图压缩后续 sprint** —— 直接顺延所有 sprint，
然后回顾找根因。常见根因：
- 真实数据 + 真实集群比单测难得多（accept 它）
- 跨服务边界 race condition（设计阶段没考虑到）
- 第三方依赖坑（CBC / Highs / S3 SDK 在 Windows 上的小坑）
